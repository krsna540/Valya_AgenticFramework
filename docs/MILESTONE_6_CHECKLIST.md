## What was built

### 1. Image extraction into DocumentDOM (§6 Stage 2)
- `backend/app/ingestion/extractors/pdf.py` — every `page.images` entry is rasterized (bbox cropped from a rendered page image via `pdfplumber`'s existing `pypdfium2` dependency — not a lossless extraction of the original embedded stream, but a real, viewable, content-addressable PNG, which is what captioning/thumbnails/citations actually need) into a `Block(type="image")` plus a side-list `ExtractedImage` (sha256 + raw bytes). `extract()`'s return type changed from `DocumentDOM` to `tuple[DocumentDOM, list[ExtractedImage]]` — every call site (activities.py, dry_run_service.py, both test files) updated.
- `backend/app/ingestion/dom.py` — `ImageBlock` gained `minio_image_uri`/`thumbnail_uri` (both `None` immediately after extraction; filled in by `extract_pdf_activity` before `canonical.json` is written). Raw image bytes are deliberately NOT embedded in the DOM JSON — see the extractor's module docstring for why base64-in-JSON for every image would bloat `canonical.json` for no reason.
- OCR is still **not implemented** — `ImageBlock.ocr_text` stays `None` from the extractor; only the VLM's caption call has any chance of reading in-image text, and that isn't dedicated OCR. A real, documented gap (see below), not faked.
- `backend/tests/test_pdf_extractor.py` — new test generates a real PDF with an embedded PNG (via reportlab) and asserts a real image Block + real PNG bytes come back.

### 2. VLM captioning activity (§6 Stage 3)
- `vlm-captioner/app/main.py` — full rewrite. The Milestone 0 stub's contract was actually broken: `CaptionRequest` only carried `image_sha256`, with nothing for the service to caption (it has no MinIO access of its own). The real contract sends `image_base64` (the actual pixels) alongside `surrounding_text`/`breadcrumbs`; real Qwen2-VL-7B inference via `transformers`, lazy-loaded on first call — same pattern as `embedder/`/`reranker/`.
- `backend/app/services/vlm_captioner_client.py` — thin HTTP client (base64-encodes the raw bytes), same shape as `embedding_client.py`/`reranker_client.py`.
- `backend/app/ingestion/activities.py`'s new `caption_images_activity`, inserted between extract and chunk (`IngestDocumentWorkflow` — chunking reads `Block.display_text`, which for an image is `alt_text + ocr_text`; an un-captioned image chunks to empty text, so caption MUST run first). For each image block: check the `image_captions` cache by sha256, else fetch the raw bytes back from MinIO and call vlm-captioner, then write `alt_text`/`ocr_text` back into the DOM and re-persist `canonical.json`.
- **Caching**: `config_db_scripts/010_multimodal.sql`'s `image_captions` table, keyed by `image_sha256` alone (not document-scoped like Milestone 4's contextualization cache — see that migration's header comment and `app/models/image_caption.py`'s docstring for the tradeoff this implies: a cache hit skips re-reading the surrounding-text context passed at caption time).
- `app/pipelines/schema.py`: `image_captioner` moved from `KNOWN_WORKERS`-only into `EXECUTABLE_WORKERS` (Milestone 6). `dry_run_service.py` gained a matching branch (samples the first extracted image, real uncached VLM call, not persisted — same contract as the other dry-run branches).

### 3. SHA-256 image storage + thumbnails
- `backend/app/services/image_storage.py` — `store_image()`: content-addressed by `(tenant_id, project_id, sha256)` — deliberately NOT also keyed by document_id/version (unlike `interim/` chunk artifacts), so the SAME image reused across documents or reindexed is stored exactly once per project (checked via `head_object` before writing). Generates a thumbnail (Pillow, max 320px, JPEG q80) alongside the original. Uses the `images/` MinIO prefix that `app/services/bootstrap.py` has seeded per project since Milestone 1 but never had a writer until now.
- `backend/tests/test_image_storage.py` — 3 tests against a tiny in-memory fake S3 client (no MinIO needed): first upload writes both objects, a second upload of the same sha256 is a no-op, a different sha256 is stored independently.

### 4. Multimodal retrieval + modality cap activation
- `backend/app/models/chunk.py` / `config_db_scripts/010_multimodal.sql` — `chunks.modality` ("text"|"image"), `image_sha256`, `minio_image_uri`, `thumbnail_uri` columns.
- `backend/app/ingestion/chunking.py` — `ChunkSpec` gained `modality`/`image_*` fields; `_chunk_atomic_block` tags an image block's parent+child pair `modality="image"` and carries the image reference fields through (tables/code stay `"text"` — their content is genuinely textual, unlike an image's pixels).
- `backend/app/ingestion/indexing.py` — `IndexItem` gained `modality`/`image_uri`/`thumbnail_uri`/an optional `image_clip` vector; `build_point()` writes these into the Qdrant payload and (only when actually provided) the `image_clip` named vector that's been reserved since Milestone 2 but never populated until now. No real CLIP model is wired this milestone — `image_clip` stays `None` for every point today (§B.3.1 discipline: don't write vectors you don't actually have), left as the integration point for a future image-embedding model.
- `backend/app/services/retrieval_service.py` — `RetrievedChunk.modality` is now read straight off the Qdrant payload (`payload.get("modality", "text")`) in both the parent-promoted and direct-surface branches, instead of always defaulting to `"text"`. This is what makes Step 6's modality-balance cap (wired as a structural no-op in Milestone 4) finally have something real to bind on. `image_uri`/`thumbnail_uri` are carried through too.
- `backend/app/schemas/chat.py` / `chat_service.py` — `Citation` gained `modality`/`thumbnail_uri` so a chat answer's image citations are distinguishable from text ones.
- `backend/app/services/qdrant_admin.py` / `virtual_cluster_filters.py` — `modality` added to both `_KEYWORD_INDEXES` and `SUPPORTED_FILTER_FIELDS`, so an admin can create an "Images only" virtual cluster (`{"field": "modality", "op": "eq", "value": "image"}`) — ties Milestone 5's virtual clusters together with Milestone 6's new field.
- Frontend: `VirtualClustersPage.tsx`'s field picker includes `modality`; `ChatPage.tsx` renders a "🖼 (image result)" label for image citations (see known gaps below for why not an inline `<img>`).

## Known gaps / not done in this pass

- **Rasterized, not lossless, image extraction.** `pdf.py` crops a rendered page image rather than pulling the original embedded stream bytes — correct and viewable, but a JPEG-in-a-PDF gets re-encoded as PNG at 150 DPI rather than passed through byte-for-byte. Acceptable for search/captioning/citation purposes; would matter if a future feature needed the exact original file.
- **No OCR engine.** `ImageBlock.ocr_text` is never populated by the extractor itself (no tesseract/equivalent wired) — only the VLM captioner's own reading of in-image text (via its `OCR:` response field) has any chance of surfacing text-in-images, and that's opportunistic, not dedicated OCR. A scanned/image-only PDF page would still extract essentially nothing.
- **No real CLIP model.** `IndexItem.image_clip` and Qdrant's `image_clip` named vector (reserved since Milestone 2) are wired end-to-end but never populated — every image chunk is only findable via its caption+OCR text embedding (BGE-M3, same as any text chunk), not via genuine image-to-image or image-to-text-embedding similarity. This is a real capability gap, not just an unused field — flagged as the natural next step if image-heavy corpora need better recall than caption-text search provides.
- **Chat citations can't render an actual `<img>` yet.** `thumbnail_uri` is an `s3://...` reference — not a browser-loadable URL. The frontend shows a "(image result)" label rather than a broken image tag. A presigned-URL endpoint or a thumbnail-proxy route (`GET /.../images/{sha256}/thumbnail`) is the natural fix, deliberately out of this milestone's scope.
- **Image caption cache has no invalidation.** If the same image is captioned once with one `surrounding_text` context and then genuinely needs a different caption because it means something different in a new context, the cache (keyed purely by `image_sha256`) will keep serving the first caption forever. Documented as an accepted tradeoff (same class of judgment call Milestone 4 made for contextualization caching), not silently ignored.
- **RAPTOR (Milestone 5) never summarizes over image chunks.** `raptor_summarize_activity` clusters whatever embeddings it's handed (currently only text-child embeddings from `embed_chunks_activity`'s output) — image chunks are embedded and indexed but not fed into RAPTOR clustering. Whether images *should* participate in RAPTOR summarization is a real open design question, not obviously a bug, and wasn't in this milestone's pasted scope.
- **Modality cap is real but untested against a real corpus.** The algorithm itself is proven (`test_modality_balance.py`'s synthetic cases, unchanged from Milestone 4) and now proven to receive real `modality="image"` payloads end-to-end (`test_hybrid_search_pipeline.py`'s new test) — but no real image-heavy document has ever been ingested to see the cap actually reject an over-represented image result in production-shaped data.
